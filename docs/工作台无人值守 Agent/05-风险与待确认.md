# 05 · 风险与待确认

## 1. 需要拍板

### Q1. Home 默认视图改成「工作台」，接受吗？

影响：现在打开桌面端看到的是「项目 + 最近会话」，改后看到「项目 + 工作台」，最近会话要一次点击。

建议：接受。工作台是每天第一眼要看的东西，会话列表是一次点击的成本。

如果想两全，可以做成「记住上次视图」：默认工作台，用过会话就记住会话。代价是两台机器/多次重启后表现不一致，不如固定默认直观。

**需要你选：固定默认工作台 / 记住上次视图。**

---

### Q2. 令牌从哪来？

三条路，成本不同：

| 方式 | 成本 | 体验 |
| --- | --- | --- |
| 粘贴 `accessToken` | 最低 | 用户要从 yunxiao-web 复制一次 |
| 从报工绑定导入（`frontend-server` 已存 `yunxiaoToken`） | +0.5d | 已报工过的人一键导入 |
| 两者都要 | +0.5d | 覆盖最全 |

建议：**两者都要**。粘贴兜底，导入省事。都要的话在设置里给两个入口，导入失败自动回落到粘贴。

---

### Q3. 空间 → 项目：自动建议 + 人工确认，接受「未确认不参与可做性」吗？

现状：云效空间名和 `code_projects.project_key` 不是一一对应，光靠名字匹配会有歧义。

建议：

- 能唯一匹配的，标「自动」并允许一键确认。
- 匹配不到或多头匹配的，显示「未绑定」，**不参与「可做」判定**，只参与「阻塞」。
- 确认结果存 `spaceBindings`，一次配好长期有效。

不接受的话就得让模型猜，或者每次刷新都问一次，都不合适。

---

### Q4. worktree 怎么定位？

`crew-app-front-3.0-worktree`、`crew-app-front-3.0-worktree1` 这类目录，有两种处理：

**A. 作为项目的一个可选工作区**（建议）
`ProjectBinding { main, worktrees[] }`，详情里可切换看哪个工作区的分支和 dirty。一条云效单仍然属于「crew-app-front-3.0」这个项目。

**B. 作为独立绑定的实体**
每个 worktree 单独绑一个云效空间/项目，能精确对应不同航司分支。

A 更简单，符合「一个项目多份工作副本」的心智；B 更精确但配置量翻倍。

建议 A。如果实际场景里 worktree 是按航司长期存在的（比如 `-worktree` 专供 TG），再考虑 B。

---

### Q5.（V2 再定）「发布」具体指什么？

三种可能，实现差别很大：

1. 只是 push 分支 + 建 MR（最常见）。
2. 触发项目已有的 CI 流水线。
3. 执行项目里的部署脚本。

建议 V2 只做 1，把 2/3 作为「项目白名单命令」，默认关闭、需二次确认。V1 不受影响，但先对齐语义，避免 V2 返工。

## 2. 技术风险

| # | 风险 | 影响 | 概率 | 应对 |
| --- | --- | --- | --- | --- |
| R1 | 云效无组织级待办接口，必须项目 × 类别遍历 | 慢、限流 | 高 | 项目白名单、并发 4、60s 缓存、单项目失败降级 |
| R2 | 空间与项目不是一对一 | 分错项目 | 高 | 自动建议 + 人工确认；未确认不算可做 |
| R3 | 本地分支与环境表分支长期不一致 | 改错分支 | 高 | 明示「本地 X / 环境 Y」，标 partial；V2 开工前强制确认 |
| R4 | worktree 目录被误当项目 | 映射混乱 | 中 | 不靠扫描发现，只认显式配置；`main` 优先 |
| R5 | `safeStorage` 在部分 Linux 不可用 | 令牌不能持久化 | 中 | 降级为会话内存 + 明确提示 |
| R6 | 主进程越权读文件 | 安全 | 中 | `realpath` + 前缀校验；拒绝软链逃逸 |
| R7 | 渲染进程重新渲染卡顿（300 条） | 体验 | 中 | 列表虚拟化（>150 条）、详情按需 |
| R8 | 定时器与手动刷新竞态 | 重复请求 | 中 | in-flight 去重 + `setTimeout` 递归 |
| R9 | 桌面端 web 构建没有 `window.electron` | 报错 | 中 | `api.workbench` 为空时进「仅桌面端」空状态 |
| R10 | 主进程 RPC 改动影响现有 handlers | 回归 | 低 | 只 merge 新组，不改现有签名 |

## 5. 建议先做的 3 个 spike

| Spike | 目的 | 通过标准 |
| --- | --- | --- |
| S1 聚合耗时 | 7 项目 × 3 类别，串行/并发各跑一次 | 单轮 < 15s，无 429，条数与页面一致 |
| S2 映射准确率 | 用 20 条真实单跑 space→project→workspace→branch | 正确率 ≥ 95%，错例能解释 |
| S3 轮询稳定性 | 5 分钟一轮跑 4 小时 | 无重复请求、无内存增长、无 429 |

S1 和 S2 不通过，就不要开工写界面。

## 6. 明确不做

- 不做服务端 24/7 轮询与推送通知。
- 不做自动改云效状态、自动合并、自动部署。
- 不做多租户与团队权限（先单人单令牌）。
- 不做需求池 / 迭代 / 看板配置。
- 不在 V1 接 LLM 判可做性。
