# 02 · 技术架构与数据模型

> 全部落在 `pier/tools/opencode` 内：渲染进程 `packages/app`，主进程 `packages/desktop`。

## 1. 模块划分

### 1.1 渲染进程（新增）

```text
packages/app/src/workbench/
├─ route.tsx           # 工作台根组件，挂进 Home 右栏
├─ model.ts            # 控制器：加载、刷新、筛选、选中、轮询
├─ api.ts              # window.electron.workbench.* 的薄封装 + web 降级
├─ types.ts            # 与主进程共享的视图类型（import type）
├─ view.tsx            # 布局：工具条 / 统计条 / 筛选 / 列表 / 详情
├─ view.css            # 只写 token 无法表达的部分（grid、滚动、动画）
├─ list.tsx            # 列表与行
├─ detail.tsx          # 概览 / 映射 / 上下文 / 评论
├─ settings.tsx        # 设置浮层：根目录、令牌、轮询、项目路径
├─ manual.tsx          # 手动添加/编辑对话框
├─ home-view.tsx       # Home 右栏的「工作台 | 最近会话」切换头
└─ format.ts           # 相对时间、字节、状态文案
```

修改：

```text
packages/app/src/home/route.tsx        # 按视图切换宽度与右栏内容
```

`layout.tsx` 不动：当前视图（工作台 / 最近会话）和筛选偏好都写进 `workbench` 自己的 state，避免给 layout schema 加字段和迁移。

### 1.2 主进程（新增）

```text
packages/desktop/src/main/workbench/
├─ index.ts            # Service + Layer，组装下面几个模块
├─ settings.ts         # 读写 SQLite state / namespace=workbench
├─ secret.ts           # safeStorage 加解密 + userData 文件
├─ yunxiao.ts          # 调 frontend-server /agent-api/yunxiao/*
├─ scan.ts             # 本地目录 + 只读 git 命令
├─ resolve.ts          # space → project → workspace → branch
├─ readiness.ts        # 确定性三态规则
├─ manual.ts           # 手动工作项 CRUD
└─ snapshot.ts         # 内存缓存 + 合并快照
```

新增 RPC 定义与处理器：

```text
packages/desktop/src/shared/ipc-rpc/workbench.ts   # Rpc 定义 + Schemas
packages/desktop/src/main/ipc-handlers/workbench.ts
packages/desktop/src/shared/ipc-rpc.ts             # DesktopRpcs.merge(..., WorkbenchRpcs)
packages/desktop/src/main/ipc.ts                   # handlers 合并 workbenchHandlers
packages/desktop/src/renderer/api-types.ts         # ElectronAPI 增加 workbench 命名空间
packages/desktop/src/renderer/api.ts               # 实现 invoke 映射
```

约束：渲染进程不直接 `fetch` 云效，也不读 token。所有外部请求和磁盘访问都在主进程。

### 1.3 为什么走主进程而不是渲染进程直接请求

| 问题 | 直接请求 | 走主进程 |
| --- | --- | --- |
| 云效 token | 落在渲染进程内存/可被页面脚本读走 | 只在主进程 + safeStorage |
| CORS / CSP | 需要放宽 `connect-src` | 不需要改 |
| 本地目录扫描 | 渲染进程没有 fs 权限 | Node fs 可用 |
| 统一缓存/降级 | 每个窗口各算一遍 | 一处缓存 |

## 2. 数据流

```text
Home 挂载
  └─ workbench.model.mount()
      ├─ WorkbenchGetState()            # 返回 settings + 缓存快照（可能为空）
      ├─ 有缓存 → 先渲染
      └─ WorkbenchGetState({force:true}) # 冷启动强制一轮
            ├─ token 未配置 → state.token.configured=false，界面引导
            └─ 主进程 refresh()
                 1. yunxiao.userCurrent()          → userId / memberName
                 2. yunxiao.projects()             → spaceId / spaceName
                 3. settings.projects（enabled）    → 项目白名单
                 4. 按 项目 × 类别 并发 search(assignedTo=userId)
                 5. 本地 scan（每个项目一次，5 分钟缓存）
                 6. resolve(space → project → workspace → branch)
                 7. readiness(item)
                 8. 合并 manual items
                 9. 排序、截断、汇总 counts/warnings
                10. 写入内存缓存，返回
```

定时刷新只在渲染进程存在：

```ts
// 伪代码，实际用 setTimeout 递归，不用 setInterval
let timer: number
const schedule = () => {
  timer = window.setTimeout(async () => {
    if (document.visibilityState === "hidden") return schedule()
    await refresh()
    schedule()
  }, interval())
}
```

- 页面隐藏时清 timer；重新可见且 `now - lastSuccess > interval` 立即刷新一次。
- 同一时刻只允许一个 `WorkbenchGetState` 在飞；重复触发复用同一个 Promise。
- 失败退避 5 → 10 → 20 → 30 分钟；手动刷新重置。
- 主进程再加 60s 缓存兜底：两个窗口或快速切视图不会重复打云效。

## 3. RPC 设计

沿用现有 Effect RPC 模式（`packages/desktop/src/shared/ipc-rpc/*.ts`）：

```ts
// workbench.ts（节选，完整见 03-API契约.md）
export const WorkbenchGetState = Rpc.make("WorkbenchGetState", {
  payload: { force: Schema.optionalKey(Schema.Boolean) },
  success: WorkbenchSnapshot,
})
```

命名与现有 `StorageItems` / `FilesOpenPath` 保持一致：`Workbench` 前缀 + 动词。

返回一律是「一份完整快照」，不做增量 patch。理由：条目规模 ≤ 300，快照几 KB，增量协议带来的复杂度不值得。

## 4. 存储

### 4.1 配置与手动项 → SQLite state

复用 `packages/desktop/src/main/storage` 的 `createStateStore`（表 `state(name, key, value, updated_at)`，`drafts.sqlite`）。

namespace：`workbench`

| key | 内容 | 大小 |
| --- | --- | --- |
| `settings` | `WorkbenchSettings` JSON | < 8 KB |
| `manual-items` | `ManualItem[]` JSON | < 64 KB |
| `view` | 筛选/排序/自动刷新偏好 | < 2 KB |

- 只走 `state.items(name)` / `state.update(name, insert, remove)`，不新建表；这样和现有持久化、快照、迁移机制天然一致。
- 写入合并成一个 key 一次写，避免多行半更新。
- 读失败（JSON 损坏）→ 回落默认值 + 主进程日志，不崩。
- 不存快照：启动先空列表 + 骨架，比展示过期数据更诚实；冷启动一轮通常 < 6s。

### 4.2 令牌 → safeStorage

```text
userData/
└─ workbench/
   ├─ token.bin        # safeStorage.encryptString(token) 的密文，权限 0600
   └─ token.meta.json  # { memberName, userId, savedAt }
```

- 写：`safeStorage.encryptString(token)` → `Buffer` → `fs.writeFile(path, buf, { mode: 0o600 })`。
- 读：`safeStorage.decryptString(buf)`。
- `safeStorage.isEncryptionAvailable() === false`（部分 Linux 无 keyring）→ 不落盘，只在内存保留本次会话，并在设置里明示「本次有效，重启需重新输入」。
- 删除：删文件 + 清内存 + 清快照里的 token 状态。
- 日志里只出现 `tokenHash = sha256(token).slice(0, 8)`。

不放 SQLite：`drafts.sqlite` 是明文库，`strings` 就能捞到。

不放 macOS Keychain 自研封装：`safeStorage` 在 macOS 背后就是 Keychain，没必要多一层。

### 4.3 令牌从哪来

V1 提供两条路：

1. **粘贴**：用户在 yunxiao-web 的令牌配置里复制 `accessToken`，粘到工作台设置，点「验证」→ 调 `user/current`，成功才保存。
2. **复用报工绑定**（可选增强）：`frontend-server` 的报工绑定里已存 `yunxiaoToken`（`src/agent/services/report.ts`）。提供一个「从已绑定账号导入」，主进程调服务端接口取当前用户令牌，导入后仍然加密落本地。

不读浏览器 localStorage：跨进程读不到，也不该做。

## 5. 数据模型

```ts
export type Readiness = "ready" | "partial" | "blocked"
export type ItemSource = "yunxiao" | "manual"

export interface WorkbenchItem {
  id: string                    // 云效 id；手动项为 manual:<uuid>
  source: ItemSource
  serial: string                // TG-3223 / MANUAL-1
  title: string
  url?: string                  // 云效链接；手动项为用户填的链接
  category: "Req" | "Task" | "Bug" | "Other"
  status: string                // 云效状态名
  priority?: "P0" | "P1" | "P2" | "P3"
  airlineCode?: string
  spaceId?: string
  spaceName?: string
  projectKey?: string
  branch?: string
  createdAt?: string
  updatedAt?: string
  commentCount: number
  attachmentCount: number
  readiness: Readiness
  reasons: ReadinessReason[]
  missing: string[]
  mapping?: WorkspaceMapping
}

export interface ReadinessReason {
  level: "pass" | "risk" | "block"
  code: string                  // MAPPING_OK / BRANCH_DRIFT / ACCEPTANCE_MISSING ...
  message: string
}

export interface WorkspaceMapping {
  projectKey?: string
  workspacePath?: string        // 命中的绝对路径（main 或 worktree）
  workspaceKind: "main" | "worktree" | "missing"
  workspaceCandidates: Array<{ path: string; kind: "main" | "worktree"; exists: boolean }>
  gitRemote?: string
  currentBranch?: string
  envBranch?: string
  branchMatch?: boolean
  dirty?: boolean
  unresolvedReason?: string     // PROJECT_UNKNOWN / PATH_MISSING / NOT_GIT / BRANCH_MISSING
}

export interface WorkbenchSettings {
  frontendServerUrl: string     // 默认 http://127.0.0.1:9522
  projectRoot: string           // 默认 /Users/user/Desktop/work/pier
  toolsRoot: string             // 默认 <projectRoot>/tools
  pollIntervalMs: number        // 默认 300000
  maxItems: number              // 默认 300
  includeWorktrees: boolean     // 默认 true
  debugRaw: boolean             // 是否在详情里显示原始 JSON
  projects: Record<string, ProjectBinding>

}

export interface ProjectBinding {
  enabled: boolean
  main: string                  // 相对 projectRoot
  worktrees: string[]           // 相对 projectRoot，可空
  verifyProfile?: string        // V2 用：web-vue / uni-app / node-service / bun
}

export interface SpaceBinding {
  projectKey: string
  airlineCode?: string
  confirmed: boolean
  source: "auto" | "manual"
}

export interface ManualItem {
  id: string                    // manual:<uuid>
  serial?: string
  title: string
  projectKey: string
  workspace?: string            // 相对路径；空=main
  branch?: string
  airlineCode?: string
  priority?: "P0" | "P1" | "P2" | "P3"
  url?: string
  note?: string
  createdAt: string
  updatedAt: string
}

export interface WorkbenchSnapshot {
  settings: WorkbenchSettings
  token: { configured: boolean; memberName?: string; userId?: string; persistent: boolean }
  sync: {
    at: string | null
    durationMs: number
    ok: boolean
    partial: boolean
    warnings: Array<{ scope: "project" | "global"; key?: string; code: string; message: string }>
  }
  projects: ProjectStatus[]
  items: WorkbenchItem[]
  counts: { total: number; ready: number; partial: number; blocked: number; unbound: number }
}

export interface ProjectStatus {
  projectKey: string
  airlineCodes: string[]
  main: string
  worktrees: string[]
  resolvedWorkspace?: string
  exists: boolean
  isGitRepo: boolean
  gitRemote?: string
  currentBranch?: string
  envBranches: string[]
  dirty?: boolean
  binding: "bound" | "unbound" | "path-missing" | "not-git" | "ambiguous"
  warning?: string
}
```

## 6. 项目解析

### 6.1 输入

| 来源 | 字段 |
| --- | --- |
| `GET /api/v1/code-projects` | `projectKey` / `gitlabProjectPath` / `defaultRef` / `enabled` |
| `GET /api/v1/airline-environments?pageSize=…` | `project`（= projectKey）/ `airlineCode` / `environment` / `runtimeCode` / `appCode` / `branch` |
| `settings.projects` | `main` / `worktrees` |
| 本地文件系统 | 存在性、git 元信息 |

`airline_environment.project` 就是 `code_projects.project_key`（控制器里用 `environment_project` 关联查询），所以航司 → 项目的映射是现成的，不需要再猜。

### 6.2 空间 → 项目

```text
1. settings.spaceBindings[spaceId] 且 confirmed → 用它
2. 否则用云效空间名做归一化匹配：
   - 去空格/标点、小写
   - 与 code_projects.project_key、gitlab_project_path 的末段、
     以及项目名的常见词（crew web / portal / app / server …）比对
3. 命中唯一 → 记为 auto（界面显示「自动」，可一键确认）
4. 命中多个或无 → unbound，不猜
```

自动匹配只做**建议**，没确认的空间不参与「可做」判定，只显示「未绑定」。

### 6.3 项目 → 工作区

```ts
const candidates = [
  { path: settings.projects[key].main, kind: "main" },
  ...settings.projects[key].worktrees.map((path) => ({ path, kind: "worktree" })),
]
```

逐个校验：

```ts
const root = await fs.realpath(settings.projectRoot)
const abs = await fs.realpath(path.resolve(root, relative))   // 不存在会抛
if (abs !== root && !abs.startsWith(root + path.sep)) throw new Error("OUTSIDE_ROOT")
const stat = await fs.stat(path.join(abs, ".git"))
const isRepo = stat.isDirectory() || (stat.isFile() && (await fs.readFile(...)).startsWith("gitdir:"))
```

- **主目录缺失不等于阻塞**：worktree 存在也能开工。默认工作区 = 第一个存在的候选，main 优先。
- 全部不存在 → `unresolvedReason = "PATH_MISSING"` → 阻塞。
- 存在但不是 git 仓库 → `NOT_GIT` → 阻塞。
- 命中目录在 `projectRoot` 外（`..`、软链逃逸）→ 直接报错，绝不使用。

### 6.4 项目 → 分支

```text
1. airline_environment 里按 (airlineCode, environment, runtimeCode, appCode) 找 branch
2. code_projects.default_ref
3. 都没有 → BRANCH_MISSING（阻塞，不猜）
```

本地分支只用于对比展示：

| 情况 | 显示 | 影响 |
| --- | --- | --- |
| 一致 | 绿色「一致」 | 无 |
| 不一致 | 琥珀「本地在 X，环境表是 Y」 | partial |
| detached HEAD | 红色「detached」 | blocked |
| 分支不存在 | 红色「本地无此分支」 | blocked |

不自动 `git switch`、不自动 `git fetch`。

### 6.5 只读 git 命令

```text
git -C <dir> rev-parse --show-toplevel
git -C <dir> remote get-url origin
git -C <dir> branch --show-current
git -C <dir> status --porcelain=v1
git -C <dir> rev-parse --verify --quiet <branch>
```

- 用 `spawn("git", args)`，参数数组，不拼 shell 字符串。
- 超时 3s，超时视为「未知」，不阻塞展示。
- 每个项目 5 分钟缓存；设置变更、手动「重新扫描」时失效。
- `status --porcelain` 只取前 50 行判断是否 dirty，不解析全部。

### 6.6 排除目录

扫描根目录找候选时排除：

```text
node_modules  dist  build  .git  .cache  backup  .worktrees
```

**不排除** `*-worktree*`：用户明确要求 `crew-app-front-3.0-worktree`、`crew-app-front-3.0-worktree1` 可用。它们只在 `settings.projects[key].worktrees` 里被显式声明，不靠扫描发现，避免把临时目录当成项目。

## 7. 可做性规则（V1，确定性）

### 7.1 三态

| 状态 | 条件 |
| --- | --- |
| `blocked` | 项目未绑定 / 无可用工作区 / 非 git / 分支缺失 / detached |
| `partial` | 映射与分支都 OK，但缺验收标准、缺复现步骤、跨端改动、无验证配置、或本地分支与环境分支不一致 |
| `ready` | 映射与分支 OK，且无 `risk` 级原因 |

### 7.2 规则表

| code | level | 条件 |
| --- | --- | --- |
| `MAPPING_OK` | pass | 空间/项目/工作区/分支全部解析成功 |
| `PROJECT_UNKNOWN` | block | 空间未绑定项目 |
| `PATH_MISSING` | block | 所有候选目录不存在 |
| `NOT_GIT` | block | 目录不是 git 仓库 |
| `BRANCH_MISSING` | block | 环境表与 `default_ref` 都没有分支 |
| `BRANCH_DRIFT` | risk | 本地分支 ≠ 环境分支 |
| `DETACHED_HEAD` | block | detached HEAD |
| `ACCEPTANCE_MISSING` | risk | 正文里没有验收标准/预期结果的迹象 |
| `REPRO_MISSING` | risk | 缺陷类缺少复现步骤 |
| `DESIGN_MISSING` | risk | 需求类提到 UI 但没有设计稿/截图附件 |
| `DEPENDENCY_MISSING` | risk | 正文提到「依赖 / 联调 / 等 XX」，但没有对应工作项 |
| `CROSS_TEAM` | risk | 同时命中前后端多个项目关键词 |
| `NO_VERIFY_PROFILE` | risk | 项目没配 `verifyProfile` |
| `DIRTY_WORKSPACE` | pass（提示） | 工作区有未提交改动：只提示，不降级 |

`missing` 只收集给用户看的短句（≤ 4 条），比如「补充验收标准」「补充复现步骤」。规则内部 code 不直接暴露给用户。

### 7.3 文本信号

只用确定性关键词，且只在前 2000 字里找：

```text
验收 / 预期 / 期望结果 / 完成标准
复现步骤 / 复现 / 重现
设计稿 / 原型 / figma / 蓝湖
依赖 / 联调 / 等后端 / 等接口
```

命中少不等于错，所以这些只产生 `risk`，永远不产生 `block`。

## 8. 云效读取策略

### 8.1 为什么必须项目 × 类别

云效没有「组织级：我的所有待办」单接口。`workitems/search` 必须带 `spaceId + category`。所以：

```text
请求数 = 启用项目数 × 类别数（Req / Task / Bug 各一次）
7 × 3 = 21 个请求 / 轮
```

`activity/query` 是按日期查活动、内部同样遍历项目，不适合 5 分钟轮询。

### 8.2 并发与超时

```text
并发上限：4
单请求超时：15s
整轮超时：60s
单项目失败：记 warning，继续其他项目
```

- `perPage = 100`，只取第 1 页。
- 总条数上限 `settings.maxItems`（默认 300），超出置 `truncated`。
- 去重键 `workItem.id`。
- 默认排除完成/取消：`statusStages` 能过滤就过滤；拿不到阶段元数据时取回后按状态名过滤，并记一条 warning。

### 8.3 排序

```text
1. readiness: blocked → partial → ready
2. priority: P0 → P1 → P2 → P3（无优先级排最后）
3. source: yunxiao → manual
4. updatedAt desc
```

## 9. 错误处理

| 场景 | 主进程 | 界面 |
| --- | --- | --- |
| `frontend-server` 连不上 | 抛 `SERVICE_UNREACHABLE` | 「本地服务未连接」+ 地址 + 重试 |
| 401 / 令牌失效 | 清 token 状态，保留设置 | 红条「令牌失效，重新配置」 |
| 429 | 保留上次快照，记 warning | 琥珀条「云效限流，已退避」 |
| 单项目超时 | 该项目的 items 缺失，记 warning | 「N 个项目拉取失败」可展开 |
| 根目录不存在 | `ROOT_MISSING` | 设置页高亮，列表只显示云效数据、全部「未绑定」 |
| 目录越界 | 拒绝，记 error | 设置页报「路径必须在根目录内」 |

原则：**永远返回一份快照**，用 `sync.ok` / `sync.partial` / `warnings` 表达问题，不靠抛异常让界面白屏。

## 10. 安全

- token 只存在主进程；渲染进程拿到的只有 `{ configured, memberName, persistent }`。
- 日志用 `tokenHash` 前 8 位，永不打印明文。
- 路径一律 `realpath` 校验在 `projectRoot` 内；拒绝 `..`、绝对路径、软链逃逸。
- git 命令参数化，不拼 shell。
- V1 不执行任何项目脚本。
- 外链走现有 `FilesOpenExternal`（主进程校验协议），不在渲染进程 `window.open`。

## 11. 测试

### 11.1 主进程

- `resolve`：项目命中、worktree 命中、全部缺失、越界、非 git、分支缺失、分支漂移。
- `readiness`：三态与规则码全覆盖。
- `secret`：加密往返、无 safeStorage 时降级、删除。
- `settings`：默认值、损坏 JSON、越界路径拒绝。
- `yunxiao`：mock 多项目、分页、401、429、超时、部分失败。
- `snapshot`：排序、去重、截断、计数。

## 12. 落地顺序

1. `workbench.ts` RPC 定义 + 空 handler + `DesktopRpcs` 合并 → 渲染进程能 `await` 通。
2. `settings` + `secret` → 存得住、读得回。
3. `yunxiao` + `snapshot` → 拿到真实条目。
4. `scan` + `resolve` + `readiness` → 每条单落到项目/分支。
5. 渲染进程界面 → 先列表，再详情，最后设置。
6. 轮询与状态 → 最后接定时器和退避。

先做 3 和 4 是为了尽早暴露「云效空间到底能不能对上项目」这个最大风险。
