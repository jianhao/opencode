# 06 · AI 处理链路与规划方案

> 状态：P0 已落地（目录选择、preflight、任务表、checkpoint、规划文档、批准执行）；P1/P2 待后续。
> 目标：点任务卡 → 规划（只读）→ 人批准 → 执行 → 测试/审查 → 人验收 → 固定动作发布并回写云效。

## 1. 当前实现与边界

P0 已经落地：

- 抽屉正文只保留工作项、描述、关联项、评论；底部操作栏：`[项目目录 ▾] [开始分析] … [打开云效]`。
- 点目录按钮弹系统目录选择器，选完写入 localStorage，下次默认用它，可随时改；**分支就是该目录当前分支**。
- 点「开始分析」先 preflight：有未提交改动才弹二次确认；确认后创建任务，在
  `<项目>/.opencode/workbench/<serial>/` 生成 brief / plan / tasks / test-plan / acceptance 与 checkpoint。
- 规划会话以只读权限启动（只允许写规划目录）。注意权限规则匹配的是「相对会话目录」的路径，写绝对路径不会命中允许项。
- 底栏按阶段给动作：规划 →「同意计划并执行 / 重新规划」；执行 →「执行完成」；待验收 →「验收通过」；
  失败或取消 →「重新规划」。阶段只由人推进，不按会话空闲自动前进（AI 停下来提问不等于活干完了）。
- 批准执行时单独记一条 `execute` 运行记录；每次阶段变更由主进程往 `log.md` 追一行「阶段记录」，
  模型漏写日志时任务也还有流水。
- 任务、运行记录、审批事件存桌面 SQLite；详情可直接预览规划文档；卡片显示「规划中 / 待确认计划 / 执行中 / 执行待确认 / 待验收 / 已完成」。

明确没有的：

- 云效空间 → 本地项目的自动绑定仍靠手选目录。
- 没有 worktree 隔离（按当前阶段决定不做），AI 直接改当前工作区。
- 主进程验证器、自动审查、发布与云效回写还没接。

## 2. 规划阶段用什么

### 2.1 候选对比

| 方案 | 产物 | 批准机制 | 优点 | 问题 |
| --- | --- | --- | --- | --- |
| OpenSpec | `proposal.md` / `design.md` / `tasks.md` / spec delta，CLI 校验与归档 | 人看 proposal/design 后确认 | 结构稳定、可校验、面向"变更"而不是"文档堆" | CLI 与实际执行链路是两套；不含测试/验收/发布 |
| Brainstorming skill | 对话 + 一份设计文档 | 对话中逐步收敛 | 适合模糊需求，能把目的/约束问清 | 是对话方法，不是可执行规范；不产出测试/验收/任务状态 |
| GitHub Spec Kit | `spec.md` / `plan.md` / `tasks.md`，斜杠命令驱动 | 分阶段人工确认 | 结构完整、社区活跃 | 偏 GitHub 工作流；Python CLI；对本项目偏重 |
| Kiro spec | `requirements.md` / `design.md` / `tasks.md`，IDE 内逐阶段批准 | IDE 内确认 | 批准门槛清晰 | 绑定 IDE，不适合嵌进现有工作台 |
| BMAD | PRD / 架构 / 故事 / 角色分工 | 多角色评审 | 覆盖全流程 | 角色和文档过重，单人日常维护成本高 |
| 自研轻规范 | 固定 4–5 个 Markdown + JSON 任务状态 | 工作台按钮批准 | 完全贴合现有状态机，零外部依赖 | 需要自己写模板和校验 |

### 2.2 推荐

**推荐：OpenSpec 的产物结构 + 自研状态机（不引入 CLI 接管流程）。**

理由：

- 我们要的是"可预览、可批准、可执行、可验收"的文档，不是再装一套工具链。
- OpenSpec 的 `proposal / design / tasks` 分层正好对应「为什么做 / 怎么做 / 分几步」，比一份大 plan.md 更好审查。
- 批准、权限、验证、发布必须由主进程控制；把执行权交给外部 CLI 会多一层不可控。

落地为固定 5 个文件（放在项目目录，便于右侧预览和随分支走）：

```text
<project>/.workbench/<serial>/
├─ brief.md        # 云效事实 + 复现 + 约束（机器生成，AI 补全）
├─ plan.md         # 方案、影响面、风险、回滚
├─ tasks.md        # 可勾选任务清单（AI 执行时逐项更新）
├─ test-plan.md    # 单测/集成/真实 UI 用例、命令、预期
└─ acceptance.md   # 验收标准、证据要求、回滚条件
```

- `.workbench/` 加进 `.gitignore`，不污染业务 diff；需要留档时归档到任务表。
- 右侧预览直接复用现有 Markdown 渲染（`session-ui` 的 markdown 组件），进入「待确认计划」时自动打开 `plan.md`，可切 `tasks.md` / `test-plan.md` / `acceptance.md`。
- 模板由工作台提供，AI 只填内容；缺章节或空任务清单视为计划不合格，不能批准。

## 3. 会话状态机

```text
未开始
  └─ 开始分析（只读权限，只允许写 .workbench/<serial>/）
        └─ 计划待确认 ──(你提意见)──> 继续规划
              └─(你同意 ✅)──> 执行中（可写代码，禁止 commit/push）
                    └─ 主进程验证 ──失败──> 执行中（带失败证据）
                          └─ 通过 ──> 自动代码审查 ──有阻塞问题──> 执行中
                                └─ 通过 ──> 待你验收
                                      └─(你验收通过)──> 发布中
                                            ├─ commit + push + MR
                                            ├─ 部署测试环境
                                            └─ 回写云效状态 + 评论
                                                  └─ 已完成
```

关键约束：

- **规划阶段强制只读**：权限层面 deny `edit/write/patch`，只放行 `.workbench/<serial>/`；不能只靠提示词。
- **批准是一个事件**：优先用底部按钮「同意计划并执行」；会话里输入「同意 ✅」也识别，但要落一条 approval 记录（谁、何时、计划版本）。
- **意见走对话**：你直接说哪里不对，AI 改 `plan.md` / `tasks.md` 后重新停在待确认，不会自动开干。
- **执行阶段禁止发布**：commit/push/deploy 不是模型能自由调用的命令，只能由主进程的固定动作执行。
- **待验收不是完成**：AI 只能提交证据（diff、命令、退出码、UI 截图、review 结论），完成状态由你点。

## 4. 测试、审查、验收

1. **验证由主进程跑**：按项目 `verifyProfile` 执行 lint / typecheck / 单测 / 构建，记录命令、退出码、耗时、日志摘要。AI 自己说"通过"不算。
2. **真实 UI 测试**：启动项目，按 `test-plan.md` 走主流程和边界；必须留截图、控制台报错、失败请求。没有证据按不通过处理。
3. **自动代码审查**：测试通过后开一个只读审查会话（或子代理），产出 `review.md`：必须修复 / 建议改进；有"必须修复"就回到执行阶段，修完重跑验证。
4. **你的人工验收**：工作台展示 diff、验证结果、review.md、预览截图；你点「验收通过」才进入发布。
5. AI 最后回复只报事实：改了什么、证据在哪、还剩什么风险，不自行宣称"完成"。

## 5. 发布与云效回写

建议拆成固定动作，每个动作独立成功/失败、可重试、幂等：

```text
commit   按模板提交（含云效号），返回 SHA
push     只推 workbench 分支，保护分支直接拒绝
mr       创建 MR，保存链接
deploy   走项目配置的白名单命令/流水线，保存环境、版本、地址
sync     回写云效：目标状态 + 评论（摘要、SHA、MR、环境、地址）
```

回写评论模板包含：

- 改了什么（来自 `plan.md` 摘要）
- 提交 SHA / 分支 / MR 链接
- 部署环境、版本、访问地址
- 验证结论与证据位置
- 回滚方式

### 5.1 触发方式对比

| 触发 | 评价 |
| --- | --- |
| git commit 后自动触发 | 不推荐作为唯一入口：任意提交都会触发（含你自己的提交、rebase、amend），部分失败难恢复，权限和审计也难收口 |
| 工作台/会话里的显式「发布」动作 | **推荐**：一次点击启动流水线，幂等、可审计、可重试 |
| CI webhook 回传 | 推荐配合：部署交给流水线，主进程轮询状态后回写云效 |

结论：**提交代码 ≠ 自动发布**。commit/push 可以是发布动作的子步骤；部署和云效回写只在显式发布动作里执行，测试环境可自动，生产永远人工。

## 6. 项目与分支的长期方案

现在的手选目录是过渡；稳定做法：

- `organizationId + spaceId` → `projectKey`，确认一次长期有效；支持"本次临时指定"。
- `projectKey + 航司/环境` → 基线分支与验证配置。
- 每条任务建独立 worktree + `workbench/<serial>` 分支，不碰你的 checkout；基线分支按配置，未配置就要求你选。
- 你本地有未提交改动不影响任务，因为 worktree 从基线 commit 创建。
- 同一任务只允许一个活跃 worktree/会话；放弃任务不自动删未合并改动。

## 7. 权限与安全

- 规划只读；执行只写 worktree；发布只走主进程固定动作。
- 云效写状态/评论需要可写令牌（当前是只读），且要先校验工作流允许的目标状态。
- 部署命令/流水线必须按项目白名单配置，不能让模型现编；同一环境加锁，避免并发部署。
- 审计表记录：谁、何时、对哪条单、做了什么动作、结果、证据链接。

## 8. 分期

| 阶段 | 内容 | 出口 |
| --- | --- | --- |
| P0 | 目录选择（已完成）+ 空间/项目/基线分支绑定 + worktree + 规划文件与右侧预览 + 只读批准门 | 一条真实单走完"分析 → 同意"且未改业务代码 |
| P1 | 主进程验证器 + 自动审查 + 待验收界面 | 一条真实单走完"执行 → 测试 → 审查 → 验收" |
| P2 | commit/push/MR/部署/云效回写固定动作 + 审计 | 1 条 MR + 测试环境地址 + 云效评论 |

## 9. 自动值守（先记录，后续讨论）

方向：新单进入后自动完成规划，按风险规则决定是否自动批准（低风险、改动面小、测试齐全），高风险仍等人；连续失败自动暂停并通知；生产发布永远人工。需要在 P2 有足够审计数据后再定规则，本轮不展开。
