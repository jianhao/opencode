# fork 维护经验总结

记录在 fork 里改代码、本地验证、打包时踩过的坑。每条都只写「现象 → 原因 → 怎么办」。

---

## 1. 环境铁律

| 坑 | 现象 | 原因 | 怎么办 |
|---|---|---|---|
| bun 版本太低 | `./.fork/build.sh` 直接抛 `This script requires bun@^1.3.14` | `packages/script/src/index.ts` 硬校验 | 升级 bun（`^1.3.14`，1.4.2 可用） |
| npm 是淘宝镜像 | `bun.lock` 莫名其妙全变（3000+ 行） | 普通 `bun install` 会把 `registry.npmmirror.com` 地址写进 lockfile | **永远** `bun install --frozen-lockfile`；`build.sh` 退出时会自动 `git checkout -- bun.lock` |
| GitHub 不通 | `git fetch upstream` 报 HTTP2 framing / 连接超时 | 网络环境 | 别急着 merge；先把本地改动和测试做完 |

---

## 2. 桌面端会把环境变量灌进你的终端（最容易踩）

在 OpenCode 桌面端里开的终端，会继承一批 `OPENCODE_*` 变量，它们会**悄悄改变 `serve` 的行为**：

| 变量 | 不处理的后果 |
|---|---|
| `OPENCODE_DISABLE_EMBEDDED_WEB_UI=true` | `serve` **不用**刚构建的内嵌 Web UI，而是去加载一份旧的 UI 资源 → 「代码明明改了，浏览器里就是没效果」，会浪费大量时间 |
| `OPENCODE_SERVER_PASSWORD=...` | `curl http://127.0.0.1:<port>/` 一律 **401** |
| `XDG_STATE_HOME=~/Library/Application Support/ai.opencode.desktop` | 测试进程会读写桌面端的真实数据目录 |

**本地验证 UI 的正确姿势：**

```sh
# 先构建
./.fork/build.sh

# 起一个干净的服务：清掉桌面端注入的变量 + 独立的数据目录
env -u OPENCODE_SERVER_PASSWORD -u OPENCODE_CLIENT -u OPENCODE_SERVER_USERNAME \
    -u OPENCODE_DISABLE_EMBEDDED_WEB_UI \
    -u OPENCODE_EXPERIMENTAL_FILEWATCHER -u OPENCODE_EXPERIMENTAL_ICON_DISCOVERY \
    XDG_DATA_HOME=/tmp/oc/data XDG_STATE_HOME=/tmp/oc/state \
    ./packages/opencode/dist/opencode-darwin-arm64/bin/opencode serve --port 4400
```

**怎么判断 UI 是不是新的**：`curl -s http://127.0.0.1:4400/ | grep -o '/assets/index-[^"]*\.js'`，
再 `grep -c <你刚加的特征字符串> ` 那个文件；或者在浏览器里看目标行为有没有生效。

## 3. Web UI 的 CSP 会拦掉「插件自己起的本地图片服务」

**现象**：桌面上能显示的图片，用 `opencode serve` 在浏览器里打开就变成破图。

**证据**（`serve` 返回的响应头）：

```
content-security-policy: ...; img-src 'self' data: https: blob:; ...
```

实测（浏览器里加载三种图片）：

| 图片来源 | 结果 |
|---|---|
| `http://127.0.0.1:<别的端口>/x.png` | ❌ 被拦，控制台报 `violates ... img-src 'self' data: https: blob:` |
| 同源（`http://127.0.0.1:<opencode端口>/favicon...png`） | ✅ |
| `data:image/png;base64,...` | ✅ |

**原因**：图片地址是「另一个端口的 http」，既不满足 `'self'` 也不在允许列表里。
**注意**：服务本身没问题（照样返回 200），是**浏览器**按 CSP 拒绝渲染。桌面端（Electron）CSP 不同，所以不受影响。

**三条路，按代价排**：
1. 插件在 Markdown 里改用 `data:` URL —— 到处都能显示，代价是正文里塞进几十上百 KB 的 base64；
2. 改 fork 的 CSP 一行：`packages/opencode/src/server/shared/ui.ts`，`img-src` 加上 `http://127.0.0.1:*`；
3. 不管它（只在桌面端用）。

**本 fork 选的是第 2 条，已经落地**：

```ts
// packages/opencode/src/server/shared/ui.ts
img-src 'self' data: https: blob: http://127.0.0.1:* http://localhost:* http://[::1]:*
```

实测（真浏览器 + 真会话，Markdown 里放 `![cat](http://127.0.0.1:8935/pixel.png)`）：

```
markdown img: src=http://127.0.0.1:8935/pixel.png  natural=[160,100]  complete=True
CSP 违规: 无
```

改之前同一张图是 `loaded: false, naturalWidth: 0`。
安全性上这**不引入新能力**：`connect-src` 本来就是 `*`，本来就允许任意请求。

## 4. 插件「加载失败后永久不可用」的两个根因

改 (b) 时才发现，只改一处是不够的：

| 层级 | 位置 | 问题 |
|---|---|---|
| 插件状态 | `packages/opencode/src/plugin/index.ts`（`InstanceState.make`） | 加载结果按目录缓存，**失败也被缓存**，所以这个实例永久没有插件，只能重启 app |
| 工具注册表 | `packages/opencode/src/tool/registry.ts`（`InstanceState.make` 里的 `custom`） | 插件工具在状态创建时被"烘"进缓存，**即使插件后来加载成功，工具列表也不会再变** |

**结论**：恢复机制必须「插件状态可重试」+「插件工具每次读取时重新收集」两件事一起做，否则只是白重试。

## 5. 测试上的两个坑

| 坑 | 现象 | 怎么办 |
|---|---|---|
| `it.instance` 用真实时钟 | 在里面调 `TestClock.adjust` 报 `testClock.adjust is not a function` | `it.instance` 内部会 provide 一个 live 的 node layer，TestClock 会被顶掉。要么改用真实时钟 + `Effect.sleep`，要么把要调的时间参数做成 env（例如 `OPENCODE_PLUGIN_RETRY_BASE_MS`）在测试里调到很小 |
| 想测 npm 行为但不想依赖外网 | 测试一联网就飘 | 测试里起一个**本地假 registry**（`Bun.serve` 只实现 `GET /<包名>` 和 tarball 下载），tarball 用 `tar` 现场打，`integrity` 用 `Bun.CryptoHasher` 现算；包目录里写 `.npmrc` 指过去 |

**反向验证习惯**：写完测试先「把修复关掉，确认测试会挂」，否则测试可能根本没覆盖到你要修的那条路径。

## 6. 构建与安装

```sh
./.fork/build.sh            # CLI 二进制（内嵌 Web UI）
./.fork/build.sh --skip-ui  # 只改服务端时更快（注意：会得到没有 Web UI 的二进制）
./.fork/build.sh desktop    # 桌面端 DMG + zip（未签名、不发布）
```

产物：
- CLI：`packages/opencode/dist/opencode-darwin-arm64/bin/opencode`
- 桌面端：`packages/desktop/dist/opencode-desktop-mac-arm64.dmg`、`.zip`、`mac-arm64/OpenCode Dev.app`

### 桌面端打包的 4 个坑（都已在 `.fork/build.sh` 里兜住）

| 坑 | 现象 | 原因 / 处理 |
|---|---|---|
| electron-builder 在仓库根目录跑 | `sh: electron-builder: command not found`，且找不到 `--config` | 可执行文件与 `electron-builder.config.ts` 都在 `packages/desktop/`，必须 `cd` 进去再跑 |
| **dev 渠道的桌面端会内嵌「上游 CLI」** | 界面是新的，服务端改动全不生效 | `packages/desktop/scripts/prebuild.ts` → `downloadCliToResources()` 会去 registry 下载 `@opencode-ai/cli-*@0.0.0-next-16350`。脚本里改成用 fork 自己构建的 CLI 覆盖 `packages/desktop/resources/opencode-cli`（覆盖后要 `codesign --force --sign -`） |
| Electron 二进制下载超时 | `connect ETIMEDOUT ...:443` | 走 `ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/`（脚本已设默认值，可用环境变量覆盖） |
| `dmg-builder` 的辅助包下载超时 | 卡在 `building target=DMG` 然后 ETIMEDOUT | 它要从 GitHub 拉 `dmgbuild-bundle-*.tar.gz`（这个不受 ELECTRON_MIRROR 影响）。第一次成功后会缓存在 `~/Library/Caches/electron-builder/dmg-builder@<ver>/`，之后离线也能打；换新机器/清缓存后需要一次能连上 GitHub 的下载 |

**dev 桌面端与正版互不影响**：`appId = ai.opencode.desktop.dev`、`productName = OpenCode Dev`，
和正版（`ai.opencode.desktop`）是两个独立 app，可以同时装。

同一份 fork CLI 也可以单独装：
```sh
cp packages/opencode/dist/opencode-darwin-arm64/bin/opencode ~/bin/
```

> [!WARNING]
> **dev 桌面端和正版共用 opencode 数据目录**（`~/.local/share/opencode`：会话库、认证、配置），
> 因为 app 只覆盖了 `XDG_STATE_HOME`，没有覆盖 `XDG_DATA_HOME`。
> 想完全隔离，就从终端带着 `XDG_DATA_HOME` 启动（sidecar 会继承）：
> ```sh
> XDG_DATA_HOME="$HOME/.local/share/opencode-dev" "/Applications/OpenCode Dev.app/Contents/MacOS/OpenCode"
> ```
